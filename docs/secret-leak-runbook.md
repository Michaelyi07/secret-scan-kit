# docs/secret-leak-runbook.md — 泄密响应手册

> 适用范围：backend/ web/ miniprogram/ infra/ 四目录任一位置被 secret-scan（pre-commit 或 CI）拦截，或事后发现历史提交中存在真实密钥。
> 原则：**先止血、再清痕、后复盘**。轮换永远先于清理历史——历史里的密钥视为已泄露，即使还没被发现。

## 触发判定

| 信号 | 判定 |
| --- | --- |
| pre-commit 拦截 staged 提交 | 密钥尚未进入 git 历史 → 本地处理，未达事故级 |
| CI 在 PR/push 中拦截 | 密钥已进入至少一个提交 → **立即进入本手册四步** |
| 周期全量扫描 artifact 发现命中 | 历史密钥 → 进入四步，并加做第 3 步历史清理 |
| 外部报告（爬虫/安全研究员/云厂商告警） | 视为已泄露且可能已被利用 → 四步 + 立即检查密钥调用日志 |

## 第 1 步：立即轮换凭据（KMS）

1. 在 KMS/密钥管理系统中将该凭据标记为 `compromised`，禁止续用；
2. 生成新凭据，只写入目标环境的密钥管理（环境变量注入或 KMS 引用），**不进代码、不进群聊、不进工单**；
3. 更新部署配置并滚动重启受影响服务，验证新凭据生效；
4. 在值班日志登记轮换完成时间戳。

要点：泄露的密钥会被自动化爬虫秒级利用，轮换是唯一止血手段，任何「先查清影响面再轮换」的拖延都不可接受。

## 第 2 步：吊销云 AccessKey

1. 在云控制台（AccessKey 管理）**吊销/禁用**该 AccessKey ID 及其配对 Secret；
2. 导出该 Key 最近 30/90 天的调用日志（ActionTrail/云审计），确认是否有异常调用：
   - 有异常调用 → 升级为安全事件，同步平台安全负责人，按事件流程追损失；
   - 无异常 → 在值班日志记录「审计无异常调用」的结论与查询区间；
3. 确认该 Key 关联的资源授权（OSS/Bucket、RAM 角色）无遗留副作用。

## 第 3 步：清理 git 历史（git filter-repo）并全员重新克隆

前提：第 1、2 步已完成（旧密钥已失效，清理才有意义）。

1. 安装 `git-filter-repo`（`pip install git-filter-repo`）；
2. 在镜像副本上执行替换（示例）：

   ```bash
   git clone --mirror <repo-url> repo-clean.git
   cd repo-clean.git
   echo 'LTAI****:<the-compromised-key-id>==>REDACTED' > replacements.txt
   git filter-repo --replace-text replacements.txt
   ```

3. 强推所有分支与 tag：`git push --force --all && git push --force --tags`；
4. 通知所有成员与 CI：**删除本地克隆，重新 clone**（旧克隆仍含密钥历史）；
5. 在 GitHub 侧联系平台支持对悬空提交做 GC/缓存清理（PR 缓存、forks 需逐一确认）；
6. 重跑一次周期全量扫描，确认命中归零，截图归档。

注意：force-push 改写历史会破坏所有开放 PR，执行前与团队约定时间窗口。

## 第 4 步：事件记录与责任通知

1. 在 `docs/incident-log.md`（或工单系统）登记：发现时间、发现渠道、密钥类型、涉及文件与提交哈希、四步执行时间线、审计结论；
2. 通知责任人与其主管（渠道：工单 + IM 私信，**禁止在群里贴密钥原文或新密钥**）；
3. 复盘归因：密钥为何能被提交（缺少 pre-commit？绕过 `--no-verify`？配置文件误入库？），产出一条防复发动作（补规则/补测试/补流程）；
4. 一周后回访：确认新凭据运行正常、扫描持续零命中。
